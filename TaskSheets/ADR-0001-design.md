# ADR-0001: テキストベースの UMG を作る

- 状態: 採択
- 日付: 2026-10-02
- 利用先: point-cloud-viewer（`C:\rust\point-cloud-viewer`）の UI シェル

## 決定

**UI のレイアウトをテキストファイル（`.ui`、中身は JSON）に書き、そこから React の
TSX を生成するツール `ui-forge` を作る。** Unreal Engine の UMG の Designer に相当する
プレビュー／エディタを Tauri アプリとして持つ。

| UMG | ui-forge |
|---|---|
| `.uasset`（バイナリ） | `.ui`（JSON テキスト）。**これが唯一の正** |
| Designer | Tauri アプリのプレビュー（段階 2 以降で編集も） |
| Canvas Panel のアンカー | `Canvas` の子の `slot.anchor` |
| Horizontal / Vertical Box | `HBox` / `VBox` |
| Graph（Blueprint） | **作らない。** ロジックは手書きの TS に置く |

## 背景

AI に UI を書かせると、その場では動いても、人間が追えない形で膨らみやすい。
React の JSX は AI には書きやすいが、人間がレイアウトの正しさを読み取るには重い。
一方 UMG のようなエディタは「見て確かめる」には優れているが、保存形式がバイナリなので
差分が取れず、AI が何を変えたかを追えない。

欲しいのはこの両方である。**AI はテキストを編集し、人間はプレビューで見て確かめ、
差分でレビューする。** 同じものを、三者がそれぞれ得意な表現で扱えるようにする。

## 個別の判断

### 1. 取り込みはコード生成にする（実行時の解釈ではなく）

`.ui` から TSX を生成し、point-cloud-viewer はそれを普通のコンポーネントとして import する。
Qt の `uic` と同じ方式。

- 生成される `Props` 型が「この UI が要求する値とイベント」の一覧になる。
  ロジック側でイベントの実装を忘れると **型エラーになる**
- 本体に実行時ランタイムが増えない
- 生成物のクラス名はリテラルなので、Tailwind のクラス検出がそのまま効く
- 生成された TSX は人間が読める。何が出力されたかを隠さない

**払うもの**: 生成物をリポジトリに入れるので、`.ui` と生成物の両方が差分に出る。
生成物の先頭に「編集禁止・元は○○.ui」と書き、CI で一致を検査する。

### 2. 形式は JSON + JSON Schema

- パーサの依存がない
- JSON Schema で AI の編集を機械的に検証でき、VS Code の補完も効く
- **コメントは書けない。** エディタが書き戻す前提なので、コメントはどのみち保持しにくい。
  説明が必要なら ADR やタスクシートに書く

### 3. 書き出しは正規化する

**同じ内容なら必ず同じテキストになる**ようにする。エディタで保存するたびにキー順や
書式が変わると、差分が読めなくなる。これがこの仕組み全体の生命線。

### 4. 語彙を限定する

Tailwind のクラスや任意の CSS は書かせない。余白・角丸・面の質感などは、
`"padding": "sm"`、`"surface": "glass"` のような**列挙値**だけを選べる。
列挙値と実際のクラスの対応表は `src/core/styles.ts` の 1 箇所に置く。

- AI が独自の見た目を発明して崩す余地がなくなる
- 見た目の調整は対応表の 1 箇所で済む
- Tailwind v4 はソースを走査してクラスを検出するので、動的にクラス名を組み立てると
  壊れる。対応表にリテラルで書いておけば検出される

### 5. ロジックとレイアウトを分ける

`.ui` に書けるのは、**値の名前（bind）とイベントの名前（event）だけ**。
UMG の Graph に相当するものは作らない。UMG でも最も腐りやすいのは Graph の側だからである。

### 6. プレビューと生成物を食い違わせない

プレビューは `.ui` を実行時に解釈して描画し、本体は生成された TSX を使う。
描画経路が二つあるので、**同じ入力に対して同じ HTML を出すことをテストで保証する**
（`renderToStaticMarkup` の一致）。

## 却下した案

| 案 | 却下理由 |
|---|---|
| Slint | テキスト DSL＋ライブプレビューで発想は最も近いが、WebView を使わない独自描画のため、point-cloud-viewer の Web 版・ガラス表現と両立しない |
| 実行時解釈のみ | 型の保証が弱い。Tailwind に `.ui` を走査させる設定が別に要る |
| KDL / 独自 DSL | 読みやすさは上だが、スキーマ検証と補完の道具を自作することになる |
| point-cloud-viewer 内に同居 | 本体の履歴にツールの変更が混ざり、本体の開発がツールに飲み込まれやすい |

## 帰結

**得たもの**
- AI の編集はテキストの差分としてレビューできる
- 人間はプレビューで見た目を確かめ、値を切り替えて状態を確かめられる
- 境界（使える部品・値・イベント）がスキーマと型で機械的に守られる

**払うもの**
- 表現力は語彙の範囲に限られる。足りなければ語彙を足す（スキーマ・対応表・生成器・
  解釈器の 4 箇所を同時に変える）
- 生成物の同期を CI で検査し続ける必要がある
